# LifeWeave 插件主线：可执行建设计划与当前落点

更新：2026-09-27。产品方向和六阶段结果以 [Notion 顶层建设计划](https://app.notion.com/p/3e7af682864481d6a5f3c7f7b8542bc0) 为准；本文把它转换为工程工作包、验收和依赖，并按真实代码与运行证据更新。Git 是开发原文，Notion 镜像呈现进度。完成一条纵切不等于整个阶段完成。

## 要交给用户的东西

用户从网页或已有 Codex 会话继续同一件事：能看清系统计划使用哪些能力、实际调用了什么、用了哪个版本和背景、在哪个阶段停下；收到有来源且可再次打开的成果；指出错误后让下一轮真正改进。研发是第一种验证工作，研究和日常管理随后用同一套事项、知识与能力关系，不能被研发特例吞没。个人和团队空间当前只是本机内容隔离，多人协作另验。

产品的最小共同关系是 **事项 → 固定输入/方案 → 插件绑定 → 实际调用或观测缺口 → 成果与证据 → 评价/改进 → 新版本再用**。轻量记录、问答和讨论可以在前段停止；未收到的事件保持未知。原文只有各自的正式维护位置：本仓开发文档在 Git、平台本地知识在受控 Markdown、Notion 原生规划留在 Notion；镜像带源身份和版本，不能形成第二份互相覆盖的正文。

## 眼下的集成顺序

1. **先把已经形成的成果稳住。** 阶段 2 技术交付的 ZIP、Run 和目标提交继续可读，用户接受保持待定。本轮已补“Git 状态仍为 M、内容却在打包时变化”的拒绝检查。后续跨模块任务要用同一固定交付核验，不沿用单文件测试当作质量保证。
2. **验证本机观测的真实边界，再做插件生命周期。** 在明确受信任且已绑定的 Codex 会话中观察一次真实工具操作，核对 Hook 类型、身份、顺序和漏报；异常、停止和网络失败各保留事实。仅把确实跨过的插件 API/执行边界登记为调用，人工 `design`、`verification` 报告只是阶段声明。没有真实事件时继续显示未观测，不从模型总结补造。
3. **完成知识双端最小闭环。** 后台 Notion 需要本机受权限保护的集成令牌文件与共享给该集成的根页；现有设置接口会先读页验证，镜像器按源版本、页身份、全文回读和冲突保护发布。先用 `docs/development.md` 单篇，核对 GitHub 固定提交、Notion 页正文和状态；再用一篇确有图片的研究报告核对资产可显示。对未授权、截断、远端人工修改和旧源版本要显示失败，不能覆盖。接着让下一次新会话通过正式知识入口固定更新后的版本，旧任务仍保留旧版本。
4. **做双入口真实对照。** 从网页派一个有界代码任务，从本机 Codex 接续另一个同类任务；核对同一事项和插件目录可定位方法、知识、过程、成果、反馈与成本。两种入口的观察等级可以不同，但页面不可把不同证据画成相同的完整轨迹。
5. **再推进阶段 4—6。** 使用上述真实差距选下一条评测、领域或团队任务，不为未来插件市场、通用流程编辑器或全量本体提前铺设设施。

## 工程责任与回退

`src/lifeweave_plugins/` 只管统一描述、绑定和确实发生的调用；`DevelopmentService` 保留开发业务门禁；Runtime/Worker 保留受管 Run、隔离树和执行事件；`external_development.py` 管已有本机会话的主动报告与受支持 Hook；`NotionMirror` 管单向源版本、远端冲突与回读。前端事项页显示事实，插件目录显示同一身份，知识页负责正文和发布状态；不建第二套任务或知识库。

每条改动先保留原事项、原版本和失败证据，再做有界代码变更；用临时 PostgreSQL 测试库、前端类型/组件/构建、正式服务 API 与至少一条桌面/窄屏真实路径核对。代码和文档推到 GitHub main 后才给不可变远端链接；Notion 手工镜像与产品自动镜像分开报告。若真实工作流失败，可停用新插件调用、保留历史记录，回到已有直接事实源或上一版本；不通过改写历史计划或删除失败来“恢复绿色”。

当前外部前置只有产品 Notion 后台授权、用户对阶段 2 交付的业务判断，以及未来多人/消息连接所需身份授权。其余实现和验证可以继续在本地推进；授权前不得宣布相关门槛完成。
