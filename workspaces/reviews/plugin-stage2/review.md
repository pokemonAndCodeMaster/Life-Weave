# 阶段 2：从网页开发到可核验交付

日期：2026-09-27。状态：可实施方案稿；交由本轮主协调者在用户已授予的自主推进范围内执行。本文没有声称真实用户已经接受成果。

## 当前判断

接续两次已经跑通的网页开发，下一条结果应是：用户从同一事项交代一个有界代码改进，能明确只要方案还是允许实施；结束后直接看到并下载一份固定版本的代码交付，了解验证依据、是否进入目标仓、知识是否已更新，再显式接受或提出修改。刷新页面、换会话、实施工作树变化都不能改写已经交付和接受的版本。

阶段 1 已经实现方案、独立审阅、隔离实施、插件身份和实际调用。阶段 2 不重做这些，也不以“重新跑三个 Run”作为主要新增能力。本次最小范围按顺序是：**明确实施授权 → 固定交付包 → 关联验证、集成与接受**。

## 用户怎样完成这件事

1. 在需求或修复事项的“开发 Agent”选择“仅形成方案”或“允许按审查结果实施”。网页同时显示目标仓、基线、方法、知识和未提交改动的排除说明。用户已有明确实施授权时，可选择允许实施；不要求每个阶段重复批准。
2. 仅方案模式运行只读方案及适用审阅，到达“方案已就绪”后停止。无论文本中有没有“请实施”，服务都不能自动建立可写 Run。允许实施模式沿现有三阶段推进。
3. 实施结束后，服务从真实工作树生成固定交付包。页面先显示“补丁已交付，待核对”，给出用户可见变化、文件差异、完整补丁下载、固定版本、验证和知识变化；不显示“已合入”或“已接受”。
4. 用户或已获授权的开发者审阅并按现有 Git 流程集成。产品提供完整补丁和基线，不自动合并或推送。集成后在同一页面提交实际目标提交，服务只读核对交付文件是否与该提交一致，保留核对时间与结果。
5. 用户查看验证、实际使用结果和知识变化，点击“接受这份交付”或“需要修改”并填写说明。接受固定到这次实施 Run、交付版本和当时的集成证据；需要修改保留旧包与原因，下一轮继续同一事项。接受交付不自动完成包含其他工作的整项事项。

## 实施顺序与责任

### 第一段：明确允许做到哪一步

新增 `executionScope: plan_only | implement`，网页用普通语言展示。新请求必须明确提供，或服务默认 `plan_only`；原有数据库记录迁移为 `implement`，表示它们由旧“开发委托”入口已实际获准执行，不能追溯改写历史为未授权。请求指纹包含此字段，相同请求身份换范围必须报冲突。

方案模式仍按所选独立审阅/轻量自检走现有检查，通过后进入 `plan_ready`，不创建实施 Run。首条纵切先不提供“直接把旧方案升级可写”的新捷径：用户允许实施时创建新委托，重新固定当前背景、源码和知识，旧方案作为可阅读历史。这样不需要新增一套可变计划审批状态机。

验收：在开发页输入“先给方案”，选择仅方案；经历刷新和 worker 扫描后没有实施 Run、没有代码写入。明确允许实施的请求继续现有路径。取消、审阅不通过、基线/知识漂移的既有阻断仍有效。

### 第二段：冻结可复现交付包

在成功实施 Run 结束后生成交付候选；生成失败时明确“实施已结束，交付包生成失败”，保留 Run，不伪装运行失败，也不进入可接受状态。只对终态 Run 生成。操作按委托和实施 Run 幂等，重复刷新/网络重试不产生不同版本。

交付包由确定性代码生成，不让模型决定真实文件清单、版本或校验值。至少包含：

- 委托、事项、实施 Run、原始基线、方案哈希、审阅 Run/结论、固定输入引用；
- 完整补丁以及有序文件清单：路径、增删改、前后内容版本、文件模式，补丁和清单哈希；
- 现有实施结果正文的固定版本与入口；该正文中的测试结论标为实施者报告；
- 已排除的输入材料与可重建缓存清单；不能静默漏掉其他代码、资源或文档；
- 可观察的范围限制，及需要更新的知识引用/“无知识变化”的理由。

产物保存在 `.runtime` 下受服务管理、按交付身份定位的目录；DB 保存版本与引用，不让客户端传任意文件路径。下载读取已固定字节并核对哈希，不再读取正在变化的执行树。页面预览可截断，下载和接受均针对完整包。删除执行树后仍能读取交付包。

补丁应使用 Git 能应用的完整格式，支持删除、模式变化和二进制；未跟踪文件也必须进入相同完整性检查。若首轮工程时间只够支持受限文本修改，应明确拒绝包含不支持类型的包并列出文件，不能把其余部分当成完整成果。不得跟随符号链接读取仓库外正文。用临时目录/临时索引生成，不能改变目标仓的索引、分支或工作文件。

生成时检查工作树未在采集前后变化；变化则失败重试。固定后现场又变化，只能产生新的明确候选/新尝试，不覆盖已经展示、验证或接受的交付版本。

验收：把下载补丁应用到原始基线的一次性 checkout，得到清单中的文件内容和模式；新文件、删除、重命名或二进制至少按声明支持范围覆盖。预览截断、现场继续变化、工作树被清理，都不会改变下载内容。

### 第三段：分开验证、集成、接受

网页同一交付区呈现四个独立事实，不压成一个绿灯：

| 事实 | 谁负责 | 什么证明它 |
| --- | --- | --- |
| 实施 Run 已结束 | Runtime/Worker | 原 Run 终态、事件和退出结果 |
| 这份交付经过技术验证 | 实施者/复核者，服务保存来源 | 固定交付版本、实际检查及输出引用；接口/页面核查说明运行版本；上报与服务实际执行明确区分 |
| 这份交付已进入目标提交 | 执行 Git 的开发者；服务只读核对 | 固定目标仓、实际提交，按交付文件核对 Git 树中的内容与模式；删除项确实不存在 |
| 用户接受此结果 | 当前用户显式页面操作 | 固定交付证据、接受人、时间、判断与范围；模型和检查不得代替 |

**验证。** 不从 Markdown 中出现“通过”自动解析出已验证。现有 Run 结果和真实事件可以作为证据来源，但只是模型自述时仍标“实施者报告”。本次先记录与查看真实测试、接口/页面证据；不新建通用 CI、任意 shell 验证器或总分系统。服务可确定性核对补丁完整性、`git diff --check` 与 Git 身份，这类检查才标服务核对。技术失败或缺证据显示具体缺口，不能由一次点击掩盖。

**集成。** 提供“核对目标提交”，复用创建委托时固定的目标仓，只接受提交身份，不接受客户端换目录。按清单核对所有交付文件：新增/修改内容和模式相符，删除确实不存在。目标提交存在即可核对其历史内容；是否为当前 HEAD、目标工作树是否另有未提交改动分别显示，不能推定正在运行的服务就是该提交。只核对交付涉及的路径，不要求目标仓不能同时包含无关提交。远端推送状态需另有真实远端回读，缺失时不显示 GitHub 已发布。

用户可以先审查“补丁交付”而未集成，但页面必须明确接受范围。本次推荐提供两种范围：“接受补丁交付”与“接受目标仓中的结果”；后一种必须有匹配交付版本的集成核对。不能把接受一个可用补丁写成代码已经上线。真正完成本阶段的真实任务证据应至少有一次目标仓集成与实际页面/接口核查；产品功能上线当夜可以待用户业务接受。

**接受。** 每次请求带交付版本、决定、原因及请求身份，服务在事务中锁定委托/证据并检查空间、事项、Run、交付哈希。旧页面、错误 Run、无关证据、同请求不同决定返回 409。接受和拒绝都保留原证据；已决定的记录不能被后续请求无痕改写。需要修改时回到同一事项保留反馈，用新委托产生新 Run 和包，旧运行失败/拒绝记录不删除。

原有“接受证据”接口如果能直接处理本次交付证据，也必须复用同一版本校验；不能允许绕过新入口覆盖其决定。原事项 `accept_item()` 目前只要求任意一条已接受证据，因此不能把它的成功反推为新开发委托被接受。开发委托完成与整项事项完成分开；若从开发区提供“同时完成事项”，必须显式指定本次已接受交付并复核事项当前版本。

### 知识更新同时走完，但不扩成阶段 3

实施者负责判断本次行为变化影响哪些使用说明/架构说明，在同一隔离补丁中提交文档；“无需更新”也给出理由。复核者核对文档与实际行为一致。项目 Git 知识继续由 Git 合入负责，网页不能借本次接受动作直接覆盖只读外部原文。

集成核对后，服务通过已有 Library 读取声明文档，记录预期/当前正文版本及可发现性；已在清单中的文档无需造“刷新索引”任务。新文档只有进入 `docs/current-sources.json` 后才算当前项目知识可发现；知识正文、目录入口和下次 `TaskSources.snapshot()` 固定版本都要核对。旧委托继续保存旧版本。

可写的本地知识候选仍走原有差异、源版本检查、用户页面接受流程；不能因代码交付被接受就自动接受知识修订。两者关联同一事项即可。

Notion 继续复用逐篇发布与回读入口。产品后台目前未配置，应显示“本地已更新，Notion 未发布/待配置”；不能把本会话 MCP 发布计作产品自动同步。新授权、外部发布和真实业务接受需要用户显式动作；这不阻塞本地交付包、测试、浏览器验证与可发现性功能完成。阶段 1 尚缺的双端同源验收仍保留，阶段 2 不宣称将它消除。

## 实现边界与技术选项

采用现有开发 service、Run、evidence、activity 和 Library，不再建独立工作流、第二套知识库或新的执行器。

| 选项 | 判断 |
| --- | --- |
| 只在页面加“已完成”按钮 | 拒绝：无法说明接受了哪份代码，也可能用旧 evidence 关闭新委托 |
| 固定补丁，开发者集成，服务核对，用户接受 | 推荐：能交付真实代码并保持现有仓库/外部写入边界，范围足够一条任务 |
| 网页自动合并、解决冲突并推 GitHub | 暂缓：需要新增仓库写锁、冲突解决、推送权限及故障恢复，不是修补本次缺口的前置 |
| 重建统一流水线/通用制品与 CI 平台 | 暂缓：现有业务所有者足够；没有真实任务证明需要新系统 |

存储可优先复用 evidence 的固定 `payload` 和 `artifactVersion`，增加委托上的交付证据关联以及必要的执行范围/决策状态；集成核对作为关联交付版本的追加事实保存。若现有 evidence 不足以保证唯一性和事务一致性，允许一张小的 development delivery 表承载固定清单与决策，但不复制 Run、知识正文和插件调用历史。实现者据代码事务能力二选一，不同时建立两套事实。

优先修改位置：

- `src/lifeweave/development.py`、`development_router.py`：执行范围、交付读取/生成/决定、集成只读核对；重型 Git 采集可拆到单一 `development_delivery.py`。
- 递增迁移：执行范围、`plan_ready`、交付关联与决定；旧 `awaiting_acceptance` 不自动变已接受，不从终态补造交付包。
- `src/lifeweave/service.py` / `repository.py`：必要的 evidence 决策共用校验和原子记录，保持其他研究/知识证据行为。
- `web/src/features/lifeweave/api/development.ts`、`components/DevelopmentPanel.vue`：明确范围和交付区；内容复杂时抽出 `DevelopmentDelivery.vue`，保留原 Run 与插件过程入口。
- 现有插件合同登记实际交付/核对操作，用同一 `lifeweave.development` 与 `lifeweave.checks.repository` 身份；不要只为此创建新顶层插件。旧固定计划不回填假调用，新绑定版本照现有漂移规则处理。
- `tests/test_development.py` 及对应前端组件用例；更新已列入当前来源的 `docs/development.md`、`docs/plugin-system.md` 和交付证据。

详细外部框架不需重新调研：本次直接复用阶段 1 已选的小内核、同源实际调用和工作台阅读方式，差异是补足 LifeWeave 的代码交付和人工接受语义。它们不是另一套插件架构，也不需要替换 Codex 内层工具循环。

## 验收与交付证据

本次工程完成必须有以下真实证据，而不是只有组件测试：

1. 一次网页仅方案委托，方案/审阅可回读，服务扫描后没有实施 Run，代码未改。
2. 一次网页允许实施的有界真实改进，复用现有方案、审阅、隔离实施；看到固定交付、真实差异、调用和结果。
3. 下载包在原基线可应用，内容与清单一致；清理/变动执行树后包仍不变。故障/不支持文件有明确失败状态。
4. 目标提交核对成功与内容不符反例；“提交含代码”“当前工作树”“当前运行版本”分开说明。
5. 同一 Run 的真实验证证据可查看；网页接受/需要修改有幂等、版本冲突、跨事项/空间拒绝和拒绝后续接测试。
6. 技术验收在独立测试数据库中可以演练人工接受，但正式运行数据保持真实用户的未接受状态，不能由本轮 Agent 为闭环代点业务接受。
7. 一篇随行为变化更新的项目知识在网页可发现、正文版本匹配；后续新委托读取新版本，旧委托输入不变；Notion 缺配置明确可见。
8. 桌面与 390px 页面可完成阅读、下载和决定，刷新后状态正确；前端类型、必要组件测试、构建和相关后端回归通过。

本阶段真实任务推荐直接使用本次新增的交付流程完成一个小的可见改进，例如“交付区显示验收范围、可跳转当前知识文档”。它应有代码、页面和文档变化，规模足够验证链路但不迫使本次新建复杂业务。不能只用空仓/只读报告证明正式工程完整开发。

首条纵切工程可在当夜完成和验证；用户不在线时，最终交付应准确停在“可下载、已技术核验、待用户接受”，清楚给出用户下次打开同一事项将看到什么。需要新 Notion 后台授权和真实业务接受的部分列为明确边界，不伪造成功，也不因此停下已授权实现。

## 风险和失败处理

- **现场差异不等于固定产物。** 固定包原子生成、完整性回放优先；错误时保留 Run 及明确故障，不覆盖旧包。
- **旧 evidence 误作新交付接受。** 精确绑定委托、实施 Run、版本与空间；新旧入口共用决策检查。
- **文件已合入不等于正在运行。** Git 核对只声明提交内容，部署/页面验证单列运行环境和版本。
- **自动推进越过只读意图。** 执行范围由服务控制，不靠模型服从；默认路径及所有重试/恢复都纳入回归。
- **知识或模型自述被误标正式。** 原文位置、版本、读取与接受各自取真实事实；Notion 未发布不得隐藏。
- **迁移误接受历史。** 只迁移兼容字段；历史包和用户决定仅在真实动作后新增。回退保留新产物和证据，旧代码不展示新增功能，不破坏原委托、Run 或正文。

本次不需要用户再批准已经授权的实现与技术验证。用户后续实际要做的是审阅具体交付，在页面决定接受范围；如需 Notion 产品后台发布，再完成该连接的真实授权。主协调者负责把本稿落实为已验证能力及同一事项的真实进展，交付说明继续区分工程完成、集成事实和业务接受。
