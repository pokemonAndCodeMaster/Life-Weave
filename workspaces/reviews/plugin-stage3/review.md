# 阶段 3 首条纵切：本机 Codex 会话进入同一开发事项

日期：2026-09-27。依据：[Notion 顶层建设计划](https://app.notion.com/p/3e7af682864481d6a5f3c7f7b8542bc0)、[开发 Agent 双入口约定](https://app.notion.com/p/3e7af682864481d7b76afd527495e5df)、[Notion 知识联动约定](https://app.notion.com/p/3e7af6828644815ab620f20b9923ef98)，以及当前源码和正式事项。用户已授权自主设计实施；本文只确定可在本轮真实验证的最小范围，不把阶段 3 全部视为已完成。

## 用户结果与当前事实

用户在本机 Codex 直接处理 `item-92989f3f9ca34660` 时，能先用正式 CLI 登记当前原生会话、目标仓和固定方法/知识，再主动上报方案、实施、验证与知识变化；如果当前 Codex 会话的 Hook 已受信任，工作台还接收受支持的工具/Turn 元事件。用户打开同一事项的“开发 Agent”页，应立即看见该会话及其来源、阶段、真实 Git 状态、材料版本与观测缺口，无需去活动页寻找，也不能误以为平台自动派发了第二个 Codex。

现有 `external_development.py` 已有 `sessions`、`events`、`binding`、`hook-events` 和现场 `diff` API；`scripts/lifeweave.py external-start/report` 自动登记当前 `CODEX_SESSION_ID` 并在本机写 Hook 绑定。正式事项中已有本轮新会话 `external-42deee3c7b4f99c14652d77fc03666fb`，其开始记录固定 `da592ff` 提交、方法和四篇项目知识。网页“接着推进”和活动栏可间接看到记录，但“开发 Agent”面板只列受管三阶段委托；插件过程也只列平台受管调用。Hook 当前只上报已绑定会话的工具名、输入哈希、模型和可识别退出码，不保存原始命令或输出，不能证明全部原生动作可见。

## 第一条可实施结果

1. 在事项“开发 Agent”页增加“本机 Codex 会话”区域，直接从已有只读 sessions API 读取，按真实 `sessionId` 分组。每组显示开始时间、原生会话身份、仓库与起始提交、固定方法和知识版本；后续主动阶段与 Hook 元事件按时间排列，来源标签、Git 快照与上报检查一目了然。Hook 的 `Stop` 是一次 Turn 停止，不自动显示“任务完成”。
2. 页面与受管委托并排而不混写事实：前者标为“当前会话主动登记／有限 Hook 观测”，后者仍展示方案、独立审阅和受管 Run。一个事项可以有两类记录，但不会因浏览页面触发新运行。
3. 读取失败只影响本机会话区域；空间或事项切换清空旧结果，不显示上一事项的记录。提供手动刷新和详情展开，支持窄屏。空列表明确说“尚未登记”，而不是“没有执行过”。
4. 保留 CLI `external-start`/`external-report` 原接口、幂等身份和安全字段。阶段是否符合方案由后续审查或用户判断，页面不据报告文本伪造计划/实际插件调用。新区域能链接到开发插件详情和当前事项原始活动，形成同一任务与能力的入口关系；真正把外部会话装配成可评价的插件调用留给下一小步，须先验证会话生命周期语义。

本轮同时修补阶段 2 的固定交付采集边界：生成包前后除了 Git 状态文本，还比较选定文件的内容与模式，防止文件在两次 `status` 都显示 `M` 时被并发改写；保留现有原基线补丁回放核对。该修复不改变用户交互或交付身份。

## 实现与验收

- 前端复用现有 HTTP 和 DevelopmentPanel，新增只读组件及明确的外部会话类型；不建第二套数据库或把活动变成伪 Run。阶段记录中 `declaredInputs` 表示固定/声明，`reportedChecks` 仍是外部会话报告；`observedGit` 是服务当时读到的仓库状态；Hook 仅是收到的元事件。
- 后端只在交付采集器增加文件快照比对。对于普通文件、软链接和删除分别按字节、模式、目标与不存在状态核对；不跟随软链接到仓库外。无法安全读取的类型使生成失败，不静默排除。
- 当前本机 Codex 会话在已有正式事项再次上报一条真实设计/验证记录，网页直接读回；空间切换、空事项、API 故障、桌面与 390px 浏览器均核查。Hook 若未出现，明确记为未观测，不制造事件。
- 阶段 2 的独立数据库回归增加“同一个 `M` 状态但文件内容变了”的打包失败反例；相关后端、前端类型、组件测试与构建通过后部署。Git 和 Notion 镜像分别保留原权威；Notion 产品后端仍缺授权，不用当前交互式 MCP 权限代替。

后续阶段 3 仍须：验证受信任 Hook/原生工具覆盖，完成外部会话与插件计划/调用的真实生命周期绑定，证明不同入口复用同一方法与知识后的质量；配置产品后台 Notion 并验证全文、资产与持续变更双端回读。上述结果不是本轮界面改造可以自动宣称完成的事。
