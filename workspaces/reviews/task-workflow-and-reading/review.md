# LifeWeave：事项工作流、步骤交付与阅读体验方案

用户打开一个事项，应当立即知道事情如何推进、现在到哪一步、每一步交付了什么；从网页派任务或从本机 Codex 接续，都应留下同一套可检查的过程。此次建议同时修正成果的产生与登记方式，以及步骤弹窗和文档阅读。仅把现有长内容搬进弹窗，不能解决步骤没有交付的问题。

核对日期：2026-09-27。代码基线：`89959e1b263405b9f0d76d7e6dee135141c638a7`。

状态：**用户于 2026-09-27 回复“开干吧”，批准本方案并授权实施；实现与集成验证中。** 手机范围仍为“这轮先改工作流与阅读，手机访问稍后”。方案阶段只读核对代码、运行记录和 Notion 镜像；实施阶段接续原事项，登记真实执行、步骤与交付，不将设计内容冒充完成结果。

## 1. 用户要解决的问题

当前主要困难不在功能数量，而在于用户无法从事项中辨认真正的工作：不知道谁在执行、遵循什么步骤、每一步产生了什么、下一步怎样继续；看成果时又被重复记录和过长页面打断。

| 用户明确提出的诉求 | 这次应达到的使用结果 |
| --- | --- |
| 说明手机端到底在哪里、怎样用 | 如实说明现状；此次不建设手机访问入口，不把窄屏测试当作手机上线 |
| 说明此前由什么 Agent 执行、是否遵守开发流程、有没有统一图 | 区分当前对话的实际开发、外部登记和平台受管执行，指出不能证明的部分 |
| 新对话、新工作应该怎样归属事项或子事项 | 接入工作台的 Agent 在实际工作前判断接续、拆分或新建，避免遗漏工作和重复事项 |
| 规划应说明步骤、输出和验收标准 | 多步骤工作先交付计划；完成节点能拿出可检查的结果，不能只写“完成” |
| 点击步骤后用弹窗，避免把原页面不断撑长 | 概览保持稳定；弹窗内浏览、切换步骤、查看产物，关闭后回到原图位置 |
| 产物先给分类和树状摘要，再查看全文或代码 | 大量文件先看目录、数量和改动规模，展开到需要的文件，不平铺几百行 |
| 文档进入内部知识阅读页，支持公式、图片、框图、表格 | 内部阅读指定成果版本，保留来源与返回位置，正文和媒体能正确显示 |

现有事项、材料、历史交付及归档都要保留。Notion 继续作为镜像，原文仍在原处；Linear 继续仅作历史只读。本次不把阅读工作产物等同于发布正式知识，不扩展执行器市场、移动部署或无人值守的通用调度系统。

## 2. 已核实的现状

### 2.1 手机端还不是可访问的独立入口

当前是同一个网页的响应式布局，曾在 390px 宽的浏览器中验证。启动脚本和当前进程都只监听 `127.0.0.1:8010`；运行环境为 WSL2。不能据此向手机提供一个已经验证可用的局域网地址，也不能称为手机 App 已交付。

按照用户本轮选择，不改监听地址和网络暴露范围。新弹窗、目录与阅读页仍需适配窄屏，但手机实际连通、部署与访问控制另行处理。启动行为来源：[scripts/workbench.py](../../../scripts/workbench.py)。

## 3. 建议的事项归属与工作流程

### 3.1 对话、事项、步骤、执行各自承担什么

事项承载一个可以持续推进和验收的目标。步骤描述达成目标需要完成的工作。执行是某个 Agent 或人对步骤的一次尝试，失败重试与反馈修改可以有多次执行。对话只是进入这些工作的入口。

| 场景 | 建议处理 |
| --- | --- |
| 换会话、追问已有结果、修改同一交付、修复验收发现的问题 | 接续原事项；增加执行记录或调整计划，不因一条消息新建事项 |
| 新工作有独立成果与验收、可以单独推进或分派 | 在已有目标下创建子事项，父事项看汇总，子事项保留完整步骤 |
| 出现不同目标、没有合适上级事项 | 新建事项 |
| 只问现状、讨论方案、了解知识 | 关联已有事项背景即可；不自动开始执行或制造工作记录 |

归属判断按“用户指定的事项 → 已绑定对话/执行 → 相关事项候选”处理。明确匹配时自动接续；存在多个实质不同目标时说明候选，不悄悄选一个。创建与绑定要有幂等请求标识，同一工作从网页和本机同时进入也不能重复创建。

上轮命名与步骤详情改动可以继续归入原工作区事项。这轮跨越步骤协议、两入口、阅读能力，实施时建议在两个已有目标下拆分：

- 工作区事项下：**步骤规划与交付约束**、**步骤弹窗与产物目录**、**内部成果阅读**。
- 双入口与 Notion 事项下：**网页与本机共用事项绑定、步骤报告**；依赖前面的交付约束，并反向服务工作区。

以上是建议的工作包与关系，不是已经创建的子事项。父事项关联同一批交付，避免每个子事项再复制一遍原文。通用归属能力服务接入 LifeWeave 的 Agent；无法替未接入、未登记的任意外部 Agent 自动保证过程可见。

### 3.2 多步骤工作先产出一份真正的计划

第一步“规划与拆解”的交付物就是版本化计划，包含目标、范围、必要背景、各步骤做什么、依赖什么、谁负责、预期产物和验收办法。该步骤不需要再递归生成一套规划它自己的计划。

事项中的业务步骤由研究、开发等能力按任务定义，公共底座负责表达、存储和检查。论文研究可以是问题与材料确认、方法分析、实验与局限、综合报告；开发可以是方案、审查、实现、验证与交付。不会把所有事项强行套成相同页签，也不把每次工具调用画成一个业务节点。

明确的小修改可以使用精简计划，而不是强造多层流程。发生范围变化时提交计划的新版本，保留变化原因和旧版；既有执行仍指向当时的计划。需要方案审查的开发，在审查明确通过后才进入对应实施步骤；问题、拒绝及修订也要可见。

### 3.3 每个完成步骤都有结果，但结果不必都是文件

| 步骤性质 | 可检查的结果 | 不能用来代替交付的内容 |
| --- | --- | --- |
| 背景与调查 | 发现、来源、影响下一步的结论 | 只有“已调研”或工具调用数量 |
| 规划与设计 | 计划或设计说明及其明确版本 | 空模板、没有产物与验收的步骤清单 |
| 代码修改 | 固定版本的变更清单、diff 与必要文件快照 | 当前仓库所有改动，或随分支继续变化的链接 |
| 验证与审查 | 实际结果、证据、结论和局限 | 未执行的检查表、没有依据的“通过” |
| 操作与交付 | 操作回执、发布对象或可读交付 | 只有执行器返回成功 |
| 接受成果 | 接受或要求修改的决定及依据 | 代替用户自动标记接受 |

未开始的步骤可以尚无实际产物，但必须说明预期结果；等待是状态或条件，不能靠“等待结束”冒充有成果的业务步骤。失败、取消、不再适用各自说明原因，不为了填满图造文件。

提交完成时，服务检查预期交付是否齐全、引用是否属于当前事项与允许来源、版本是否明确、文件是否可读、证据是否登记。结果存在与内容正确分别判断：保留“Agent 陈述”“自动检查结果”“审查结论”和“用户接受”的区别，不能承诺机器仅凭有文件就能判定全部质量。

缺交付时保留报告和问题，不把步骤置为成功；用户能看到具体缺什么并继续补交。旧记录中已经完成但没有产物的节点标明“旧记录未登记交付”。只能把查证确实属于该步骤的现有材料补关联，不能伪造当时的执行或重新用当前文件冒充历史版本。

## 4. 建议的页面与阅读交互

### 4.1 点击节点打开固定高度的步骤弹窗

概览保持图、整体状态和当前关注点。点击节点后，打开大型弹窗；宽屏保留图的背景，窄屏占满可用视口。弹窗内部滚动，底层页面锁定并保留原位置。

弹窗固定头部显示步骤名、状态、前后步骤与关闭按钮；依赖关系仍按图表达，不把并行节点误写成必须串行。正文先显示简洁结论、预期与实际交付情况，再显示产物摘要。背景、采用的输入、检查详情与历史尝试按需展开，默认不平铺日志全文。

产物不默认打开长报告。用户先看到交付类型与规模，再选择内容。切换步骤只更换弹窗内容；关闭回到原图节点。支持 Escape、焦点约束与返回原触发点，刷新或浏览器返回可恢复当前事项、步骤及打开对象。后台刷新同一版本数据时不重置目录、diff 或阅读位置。

### 4.2 产物按用途分类，再按目录展开

默认入口是“文档、代码变更、验证材料、附件、决策与操作记录”的分类摘要，各类下按真实目录或成果结构折叠展示。某类没有结果就不放空卡片。测试源码属于代码变更，测试报告属于验证材料；同一文件的同一版本去重，避免分类合计重复。

代码展示总文件数、增删行数，目录展示本目录聚合数，文件显示状态和增删行；重命名保留旧、新路径，二进制显示类型和大小、不捏造行数。文档也可显示修改规模，但先让用户理解交付内容。目录只在用户展开时呈现子项，可以按路径查找及按变更状态筛选，不先铺开数百个文件。

这些数字必须来自固定版本的完整文件清单及 Git 统计，不能靠模型概括，也不能从当前截断的实时 diff 推算。固定目录数据一次完整取得，前端构树、聚合和筛选；正文与单文件 diff 按选择读取。规模验证会用代表性的多目录、数百文件夹具，而不是把这个数量做成产品硬上限。

### 4.3 选择不同产物后发生什么

| 用户点击 | 展示方式 | 返回与版本规则 |
| --- | --- | --- |
| 文档、研究报告 | 进入平台内部知识阅读页；清晰标记“工作产物”或正式知识，并显示来源与版本 | 默认读本次交付的固定版本；返回恢复原步骤和目录位置，另提供“查看当前原文” |
| 代码文件 | 弹窗内切到该文件的 diff 阅读区域，保留目录导航，可切换文件 | 查看这次交付的改动，不随当前分支漂移；超长文件在阅读区内滚动 |
| 验证报告、审查结论 | 短结果在弹窗内结构化展示；长文沿用内部文档阅读页 | 保留实际检查时间、结果、证据与所属执行 |
| 图片或其他附件 | 图片使用受控阅读区缩放；支持的附件预览，其余明确类型并下载 | 指向保存的附件，失败明确说明，不显示无效本地路径 |

不层层叠加弹窗。整份报告需要长时间阅读时进入完整阅读页；步骤弹窗负责快速判断和选择。GitHub、Notion 归档入口作为补充，不代替平台内的默认文档入口。

### 4.4 一个阅读底座，支持正式知识与交付快照

现有知识页和成果阅读复用同一正文组件，文档引用明确区分“来源、路径、当前版本”与“交付、文件、固定版本”。不能把任意 GitHub URL 改写成内部 URL 就声称文档可读：项目知识当前使用允许路径清单，交付文档还需要受控的快照读取入口。

| 内容 | 本次改进与边界 |
| --- | --- |
| 正文与章节 | 合理行宽、层次、目录与锚点；长标识不撑破页面；长报告有明确阅读定位 |
| 公式 | 复用现有 KaTeX，覆盖行内与块级公式；长公式局部滚动，语法错误保留可理解的提示和原文 |
| 图片 | 按文档所在目录和登记来源解析相对路径；研究运行包、项目文档、交付快照使用各自受控资源来源；支持查看大图，缺图给明确原因 |
| 框图 | 增加 Mermaid 渲染与放大查看；失败可查看源码，不能让一张图失败导致整篇文档不可读 |
| 表格 | 清楚的表头、间距和边界；宽表在局部横向滚动，正文布局保持稳定 |
| 代码与下载 | 可读代码块与复制；已有 ZIP/离线阅读继续可用，图片引用与导出使用同一来源解析规则 |

本轮媒体保证范围是平台已登记的项目资料、运行材料及捕获的交付快照；不承诺任意受登录限制的外部图片永远可读。相对资源必须校验来源根目录、路径和链接目标，不能开放任意本地文件读取。保留 Markdown 清理和 KaTeX 非信任模式；Mermaid 采用受控渲染，不通过放开任意 HTML/脚本解决显示问题。

Mermaid 的渲染方式与安全选项参考其[官方使用说明](https://mermaid.js.org/config/usage.html)。该选型仍须用实际架构图、中文内容、失败图和构建环境验证。

```mermaid
  D --> E[受管执行或外部执行]
  E --> F[步骤报告与固定产物]
  F --> G[完成检查与当前进展]
  G --> H[事项概览与步骤弹窗]
  H --> I[产物分类和文件树]
  I --> J[内部文档阅读或文件 diff]
  J --> K[反馈与下一次接续]
  K --> D
```

图中复用现有事项、执行器、外部会话、计划存储、交付包和知识页；主要增强共同写入规则、固定产物目录和阅读。既有活动记录继续承担追溯，不再要求用户从日志中拼出主流程。

### 5.1 模块与数据责任

当前 `payload.workPlan` 与计划活动快照可承载本次计划扩展，无需为每个新名词建一张表。正式事项状态、当前计划、历史报告、固定文件的职责要分开：计划保存当前要求和引用；多次报告及执行保持可追溯；文件正文和媒体沿用受控交付存储，数据库保存身份、关联、版本和位置。

步骤报告与当前状态更新应原子提交，使用请求去重及计划版本检查。两个 Agent 同时报告不同步骤不能互相覆盖；旧计划的报告仍保留在对应尝试中，未经核对不能更新新计划。服务重试不能生成重复节点或重复产物。

产物固定时记录输入基线、输出版本、完整清单和校验。对于外部 Agent，开始时已有的用户改动必须识别并隔离归属，不能把整个脏工作区都记到自己名下；无法稳定捕获时报告失败并保留原始记录。文件内容和引用的图片一并捕获，才能保证日后读到同一份交付。

## 6. 旧数据与旧交互怎样退出

1. 保留已有事项、执行、归档及计划快照。新计划字段向后兼容，但旧节点不能因为字段默认值就被认定已满足新交付规则。
2. 逐项核对本次涉及的两个父事项，把有证据的成果关联回来，记录补关联的时间与来源。旧受管执行图作为对应尝试的历史保留，不再代表整个父事项。
3. 新工作先登记业务计划，再通过两个入口映射步骤；旧阶段报告保留为历史记录，迁移完的生产者不再只写阶段文字却不更新步骤。
4. 步骤弹窗稳定后删除图下方的内联正文展开路径；成果页与弹窗共用同一阅读与目录能力，不各自再维护一套历史列表。
5. 新交付保证固定文件读取。旧 ZIP 若可结合其可信基线重建则经过校验后提供；否则说明缺少快照，保留旧包下载，不能把当前同名文件冒充旧版本。
6. 现有项目源允许路径不因弹窗链接而全部开放。正式知识沿用登记与发布规则，临时交付通过带身份校验的产物阅读；阅读不复制原文，不自动晋升正式知识。

每个阶段保留数据库和交付文件备份、前后对账与代码版本。失败时恢复该组变更；已有原文、旧包和历史记录始终保留，避免界面回退导致证据丢失。

### 代码怎样连接起来

网页与本机先经 `work_binding.py` 确认目标，避免入口各写一套建项规则。`work_view.py` 保存业务计划和历史快照；`work_step_reports.py` 按版本处理尝试并核对实际交付，受管开发阶段和外部报告都调用它。编辑计划不能跳过完成检查，旧版本报告保留但不覆盖新计划。

交付层在 Git 临时索引里捕获指定路径、前后文件及引用图片，不修改用户真实索引。固定包包含可直接解压的文件、补丁和清单；`output_files.py` 在核对事项与版本后供目录、文件和内部文档共用。目录不依赖旧的100文件实时diff，也不读取当前源码冒充旧交付。人工成果正文从固定证据读取，修改实体摘要不改变已交付正文。

Vue 的 `WorkStepDialog` 管弹窗与返回，`WorkOutputCatalog/WorkFileTree/WorkFileDiff` 管分类和按需细节；`KnowledgePage/MarkdownBody` 管文档与安全媒体。原文链接必须能对应已登记知识来源才显示，不凭文件同名猜测。阅读成果不调用知识发布或用户接受接口。
